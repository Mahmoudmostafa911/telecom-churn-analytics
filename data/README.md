## Synthetic telemetry — how it is generated (and why you must not over-read it)

`generate_network_kpis.py` creates one row per customer-month with:

| KPI | Fiber | DSL | No internet |
|---|---|---|---|
| `avg_download_mbps` | ~N(190, 35) | ~N(25, 6) | — |
| `avg_latency_ms` | ~N(18, 4) | ~N(42, 9) | — |
| `outage_minutes` | Poisson(10) | Poisson(18) | Poisson(5) |
| `dropped_call_pct` | Gamma(2, 0.35) for phone customers | | |
| `data_usage_gb` | ~N(260, 80) (+60 if streaming) | ~N(95, 30) (+40) | — |
| `complaints` | Poisson(0.04) baseline | | |

Each customer carries a persistent "network luck" multiplier, and **customers
who churned get a gradual degradation in the last three months of the window**
(+25 % latency per month, more outages, more complaints). That pattern is
deliberately built in so the project can demonstrate trend features, the
monthly fact table and the "does quality precede churn?" analysis. Any lift it
gives the model or any chart built on it is **illustrative, not evidence**.

## Data-quality rules applied (see `src/telco_churn/quality.py`)

* row count vs. published size (WARN), unique `customer_id` (FAIL), no nulls in keys/measures (FAIL)
* category domains for all 17 categorical columns (FAIL)
* numeric ranges: tenure 0–72, monthly 0–200, total 0–15 000 (FAIL)
* `total_charges ≈ monthly_charges × tenure` — WARN if > 5 % of rows deviate by > 50 %
* churn rate plausibility 10–45 % (WARN)
* telemetry: unique (customer, month), referential integrity to customers (FAIL), KPI ranges (WARN)
